# OrangeFlix YouTube Discovery V2 — Full Implementation Specification

## ROLE
You are a senior TypeScript/React/Firebase engineer working on OrangeFlix.

You are upgrading the existing OrangeFlix YouTube geo-discovery system from **Discovery V1 to Discovery V2**.

The goal is not merely to modify a few scoring numbers.

The goal is to build a significantly stronger, persistent, incremental, explainable YouTube discovery engine that:

1. Finds substantially more relevant movies and series for configured countries.
2. Correctly distinguishes movies, series, episodes, trailers, clips, interviews, music and unknown content.
3. Groups scattered and inconsistently named episodes into the correct series and season.
4. Remembers discoveries permanently so OrangeFlix does not repeatedly perform the same expensive YouTube searches for every user.
5. Reuses previously discovered metadata and relationships.
6. Continues discovering new content incrementally.
7. Uses a 0–100 scoring system.
8. Automatically publishes only content above the configured auto-publish threshold, following the existing trusted-channel policy.
9. Keeps uncertain content in review instead of guessing.
10. Preserves the existing trusted-channel lifecycle.
11. Provides evidence explaining why every item received its score.
12. Remains a FRONTEND-ONLY application. Do not introduce a traditional application backend.

DO NOT destroy working functionality unnecessarily.

First inspect the existing implementation and preserve compatible public interfaces where practical.

Discovery V2 should be an evolution/replacement of the discovery intelligence, not a destructive rewrite of unrelated OrangeFlix functionality.

# 3. CORE PRINCIPLE
Discovery V1 behaves approximately like:

YouTube search → videos → keyword scoring → publication.

Discovery V2 must behave like:

YouTube search
→ candidate collection
→ persistent cache lookup
→ metadata enrichment
→ geo analysis
→ content analysis
→ series/season/episode resolution
→ duplicate resolution
→ trusted-channel analysis
→ evidence aggregation
→ 0–100 confidence score
→ publication decision
→ persistent Firestore knowledge

The system must remember what it has already learned.

A user opening OrangeFlix must NOT trigger a fresh YouTube crawl.

Public users should read existing Firestore discoveries.

Discovery scans should be performed only by the existing admin/manual/scheduled discovery mechanism.

# 12. INCREMENTAL DISCOVERY
Discovery V2 must be incremental.

Never think:

```
scan = replace database
```
Think:

```
scan = discover + merge + update
```
For every candidate:

```
already known?
    |
    +-- yes → update lastSeenAt and relevant metadata
    |
    +-- no  → analyze and insert
```
Existing content should remain unless:

- unavailable
- rejected
- explicitly removed
- no longer embeddable
- moderation changes it
Do not delete old discoveries simply because a search no longer returns them.

# 16. QUERY PRIORITY
Not all queries have equal value.

Each query should have a priority:

```
HIGH
MEDIUM
LOW
```

```

  executions: number;
  usefulCandidates: number;
  highConfidenceCandidates: number;
  duplicates: number;
  rejected: number;
```

A query producing mostly garbage should be deprioritized.

Do not automatically delete administrator-created queries.

---

# 17. SEARCH RESULT BUDGET
Respect YouTube quota.

Search requests are expensive.

Before starting a scan:

1. Calculate how many queries will execute.
2. Check how many are cache hits.
3. Execute cache misses only.
4. Stop safely when quota/rate-limit errors occur.
5. Never continue blindly after quota exhaustion.
Do not make dozens of unnecessary searches simply because a country has many query strings.

# 20. TRUST SCORE
Do not make channel trust binary internally.

Maintain a 0–100 trust score.

Example inputs:

- administrator approval
- historical accepted content
- historical rejected content
- country consistency
- repeated correct classification
- duplicate/reupload rate
- metadata quality
- content quality
However:

`approved` remains an administrator-controlled trust state.

The numeric score should support ranking and discovery priority, not silently override administrator decisions.

---

# 21. CONTENT CLASSIFICATION V2
Replace the current single heuristic score with separate dimensions.

Every candidate receives:

```
geoScore: 0–100
contentScore: 0–100
seriesScore: 0–100
channelScore: 0–100
qualityScore: 0–100
duplicateScore: 0–100
```
Then calculate:

```
finalScore: 0–100
```
All scores MUST be normalized to 0–100.

Never return values above 100.

Never return negative final scores.

---

# 22. FINAL SCORE
Use a weighted average.

Suggested starting weights:

```
geoScore       25%
contentScore   25%
seriesScore    15%
channelScore   15%
qualityScore   10%
duplicateScore 10%
```
Do not let `rightsScore` imply legal verification.

Rights should remain a separate safety/publication condition.

The formula must be centralized and configurable.

Example:

```
finalScore =
  geoScore * 0.25 +
  contentScore * 0.25 +
  seriesScore * 0.15 +
  channelScore * 0.15 +
  qualityScore * 0.10 +
  duplicateScore * 0.10;
```
Round to an integer.

# 23. AUTO-PUBLISH THRESHOLD
OrangeFlix already auto-publishes qualifying content.

Preserve that behavior but make the threshold explicit and configurable.

Example:

```
AUTO_PUBLISH_SCORE = 80;
```
This is only an example.

Read the existing project's current threshold and preserve it initially unless there is a clear reason to change it.

Rules:

```
finalScore >= configured threshold
AND
hard rejection rules pass
AND
channel trust rules pass
AND
embeddable
AND
publication policy allows it
```
→ auto-publish.

Below the threshold:

```
pending_review
```
unless a hard rejection applies.

The threshold MUST NOT be hidden inside arbitrary classifier code.

# 24. HARD REJECTION RULES

# 25. MOVIE CLASSIFICATION
A movie should not be determined by duration alone.

Current V1 uses duration as a major positive signal.

V2 must use multiple signals:

Positive:

- full movie/full film terminology
- movie/film/cinema terminology
- appropriate duration
- country relevance
- trusted channel
- movie category
- coherent movie description
Negative:

- trailer
- teaser
- clip
- scene
- interview
- reaction
- review
- ending explained
- episode
- season
- music
- countdown
- news
A 70-minute episode MUST NOT become a movie simply because it is 70 minutes long.

# 71. AI PROMPT
When AI reasoning is used, send structured metadata and request strict JSON.

Use a prompt similar to:

"You are OrangeFlix's metadata reasoning engine.

Analyze the supplied YouTube metadata.

You must not invent facts.

Separate observed evidence from inference.

Determine:

1. likely country/countries
2. language/languages
3. content type
4. whether it is likely a movie
5. whether it is likely a series
6. whether it is likely an episode
7. likely series title
8. likely season number
9. likely episode number
10. contradictions
11. evidence
12. confidence from 0–100

- A long duration does not prove that something is a movie.
- An episode can be longer than 60 minutes.

- "Part 1" does not automatically mean Episode 1.
- Country and language are separate concepts.
- YouTube metadata does not prove copyright ownership.
- Do not treat rights as verified.
- If information is unknown, return null.
- Never fabricate missing metadata.
- Prefer existing OrangeFlix series knowledge when provided.
- If the candidate probably belongs to an existing series, explain why.
- If evidence conflicts, explicitly report the conflict.
- Return JSON only."
The application must validate the returned JSON before using it.

Do not blindly trust AI output.

# OrangeFlix YouTube Geo Discovery V2 — Scoring, Trust & Publication Specification
Implement the following additions and changes as part of **OrangeFlix YouTube Geo Discovery V2**.

The goal is to make Discovery V2 substantially stronger than V1 at identifying:

- Correct country/territory
- Movies
- Series
- Seasons
- Episodes
- Scattered/inconsistent episode naming
- Full movies vs trailers/clips/interviews/music/reviews
- Trusted channels
- Duplicate content
- Previously discovered content
- New content discovered during future scans
Do **not** introduce a traditional backend as a requirement. Continue using the existing Firebase/Firestore architecture and client-side discovery where currently supported. Firestore must remain the **global persistent discovery memory**, while browser memory/localStorage must remain only a performance cache.

---

## 1. PRIMARY PUBLICATION RULE — OVERALL SCORE
Discovery V2 must introduce a normalized **Overall Score from 0–100**.

This score is the highest-priority publication decision.

### Mandatory thresholds

```
0–34
    → AUTO REJECT

35–75
    → PENDING REVIEW

76–100
    → AUTO PUBLISH
```
Implement the exact logic:

```
if (overallScore < 35) {
    status = "rejected";
} else if (overallScore <= 75) {
    status = "pending_review";
} else {
    status = "published";
}
```
Do not use the old V1 score thresholds as the primary publication system.

The new V2 `overallScore` must always be normalized to:

```
0 <= overallScore <= 100
```
Never allow a score below 0 or above 100.

---

# 2. HARD SAFETY GATES
The Overall Score is the primary decision system, but certain conditions must override it.

A video must NEVER be automatically published simply because it has a high score if it violates a hard gate.

Examples of hard rejection conditions:

- Video is not embeddable when embedding is required.
- Channel is explicitly rejected.
- Video is clearly unrelated to the configured country.
- Video is clearly a trailer when evaluated as a movie.
- Video is clearly a teaser.
- Video is clearly a clip/scene/highlight when evaluated as a full movie.
- Video is clearly an interview.
- Video is clearly music content when evaluated as cinema.
- Video is clearly a review/reaction/ending explanation.
- Video is clearly news content unrelated to the intended cinema discovery.
- Video is clearly spam or irrelevant content.
- Video is a duplicate of an already rejected canonical item where appropriate.
- A known hard-exclusion pattern identifies the content as non-cinema.
Hard gates must be evaluated before automatic publication.

Therefore:

```
HIGH SCORE + HARD FAILURE
    → REJECT

HIGH SCORE + NO HARD FAILURE
    → continue to publication threshold
```
Do not allow the score system to override explicit rejection rules.

---

# 3. V2 SCORE COMPONENTS
Do not rely on one raw additive score.

Calculate separate evidence scores and then produce the final Overall Score.

Recommended normalized components:

```
countryScore
contentTypeScore
movieScore
seriesScore
episodeScore
seasonScore
channelScore
qualityScore
metadataScore
freshnessScore
duplicateScore
```
All component scores must be normalized to 0–100.

The final Overall Score must be calculated from these signals.

The exact weighting should be configurable rather than scattered throughout the code.

Create a centralized scoring configuration such as:

```
DISCOVERY_V2_SCORING_CONFIG
```
so thresholds and weights can be changed without rewriting the classifier.

---

# 4. COUNTRY SCORE
Country matching must become much stronger than V1.

Do not assume that a YouTube search query containing a country name means that the video belongs to that country.

Evaluate multiple independent signals.

Possible evidence:

### Strong positive evidence

- Channel country matches target country.
- Channel description identifies the target country.
- Video title contains target-country cinema terminology.
- Description contains target-country terminology.
- Video uses target-country language.
- Known actors/directors/producers associated with the target territory.
- Known local production companies.
- Known local television/movie brands.
- Channel is already trusted for that country.
- Historical videos from the same channel consistently belong to the target country.
- Country-specific query discovered the video.
- Multiple independent queries identify the same country.

### Negative evidence

- Video clearly belongs to another country.
- Channel country strongly conflicts with target territory.
- Title/description indicate another country's cinema.
- The content is internationally unrelated.
- Search query is the only evidence supporting the country.
Create:

```
countryScore: number // 0–100
```
A country score must be based on accumulated evidence, not a single keyword.

# 13. TRUSTED CHANNEL SYSTEM V2

```

```
A channel must NOT become trusted simply because one video scored highly.

Positive evidence:

- Multiple qualifying movies/series discovered.
- Consistent target-country content.
- Consistent cinema content.
- Historical publication success.
- Few rejected videos.

- Frequent classification conflicts.

# 15. DO NOT RUN 40 API CALLS PER CATEGORY BY DEFAULT
The requirement for 40+ keywords does NOT mean:

```
40 movie API calls
+
40 series API calls
+
40 episode API calls
=
120 API calls per country
```
That would unnecessarily consume YouTube quota.

Instead:

```
40+ keyword vocabulary
        ↓
query expansion engine
        ↓
rank candidate queries
        ↓
select high-value queries
        ↓
deduplicate queries
        ↓
execute limited query budget
```
The keyword library is large.

The active scan query set is controlled by a quota-aware ranking system.

# 16. QUERY SCORING

```
queryPriority =
    countryRelevance
  + localLanguageRelevance
  + contentIntent
  + historicalYield
  + freshnessPotential
  + channelDiscoveryPotential
```
Queries that repeatedly produce good candidates should increase in priority.

Queries that repeatedly produce irrelevant results should decrease in priority.

# 31. IMPORTANT DISTINCTION
Keywords are not classification truth.

For example:

```
"full movie"
```
does NOT prove that a video is a full movie.

Likewise:

```
"episode"
```
does NOT prove that a video is an episode.

Keywords are discovery signals.

The classifier must inspect the full metadata and relationship evidence before deciding the final content type.

# 34. DISCOVERY V2 SUCCESS CONDITION
Discovery V2 is considered successful when it can find content that V1 misses because:

- Creator uses local language.
- Creator uses a local spelling variation.
- Movie is not titled "full movie".
- Series title does not contain "series".
- Episode does not use S01E01.
- Season is missing from the title.
- Episode number is written as words.
- Episode is called "Part 7".
- Episode is simply numbered.
- New episodes are uploaded with inconsistent naming.
- Content is discovered through a trusted channel rather than a generic query.
- Existing series has missing episode numbers.
- The same content is found through multiple query families.
The engine must continuously store this discovery knowledge in Firestore and reuse it during future scans.
